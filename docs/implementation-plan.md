# Implementation plan

Status: plan only. Nothing is built. Every performance figure here is a target marked "to be measured"; none is a claim.

## 1. How to read this plan

- **Phases** follow the specification: 1 Foundation, 2 Core archiving, 3 Crawling and sources, 4 Local search, 5 Combined search, 6 Intelligent storage, 7 Discovery, 8 Knowledge packages, 9 Hardening. All nine are in scope.
- **Task IDs** use a letter per phase to avoid clashing with the priority names P1 to P4: **F** Foundation, **A** Archiving, **C** Crawling and sources, **S** Search (local), **O** Online (combined) search, **T** sTorage, **D** Discovery, **Z** ZIM and Wikipedia, **H** Hardening.
- **Scope column**
  - **MVP**: needed to satisfy an acceptance criterion.
  - **v1**: in the nine phases and planned, but no acceptance criterion depends on it; it may slip within the release without failing acceptance.
  - **Post-v1**: designed for and documented, deliberately not built. The reason is given in [section 12](#12-deferred-and-partly-deferred-requirements).
- **Each task** is small enough for one review, independently testable, and names its tests. "Unit" means Vitest with no I/O, "integration" means Vitest with real SQLite and the local fixture sites, "e2e" means Playwright against the Compose stack. **No test touches the real internet**; fixtures are local sites and fake providers.
- **Definition of done for every task:** typecheck and lint clean, tests listed pass on AMD64 and ARM64 CI, documentation updated if behaviour or configuration changed, no new network access outside the SSRF-guarded fetcher.

### Sequencing at a glance

```
 F (foundation)
  |
  +--> A (core archiving: capture one page, browse it offline, reader)
        |
        +--> C (crawling, sources, downloads, schedules, link states)
        |      |
        |      +--> T (storage: priorities, retention, eviction)  <-- needs sources + volumes
        |      +--> D (discovery)                                  <-- needs T, S, links
        |
        +--> S (local search) --> O (combined search) --> D (search-driven discovery)
        |
        +--> Z (ZIM, Wikipedia)   <-- needs A listener, S/O merge, C crawl engine
 H (hardening) runs from F onward as tests; the dedicated phase closes gaps
```

Phases 3 and 4 can overlap after A-13 (the listener) and A-08 (extracted text) exist. T-01 to T-04 (pure planner) can start as soon as the data model is migrated in F-03, in parallel with C.

**F-03 spike result (2026-11-01).** `drizzle-kit` 0.31.11 with `drizzle-orm` 0.45.4 and `better-sqlite3` 13.0.3: `generate` works against the schema and emits plain `CREATE TABLE` plus partial and `DESC` indexes, and `generate --custom` scaffolds an empty SQL file. It **cannot emit `STRICT` tables**, `COLLATE NOCASE` on a column, or `CHECK`s except ones declared by hand with `check()` (the `enum` option on `text()` is type-only). So the migrations are hand-written SQL (`packages/db/migrations/NNNN_name.sql`, applied by our own runner with checksums and a `VACUUM INTO` backup), and the Drizzle schema in `packages/db/src/schema` exists for query typing only. `packages/db/test/schema-sync.test.ts` compares column names and nullability with the migrated database, so the two cannot drift silently. `drizzle-kit generate` stays available as a diff aid (`pnpm db:generate`, output to an ignored scratch folder) and is never used to produce migrations. Deviations recorded: `download_jobs` and `crawl_jobs` are in migration 0001 (activity_log and volume_reservations point at them) with plain-integer `source_id`, `config_id` and `candidate_id` until those tables exist; the `jobs` claim index drops `run_at` from its middle (see [benchmarks.md](benchmarks.md) and data-model.md section 3.5).
