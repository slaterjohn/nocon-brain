# Implementation plan

Status: plan only. Nothing is built. Every performance figure here is a target marked "to be measured"; none is a claim.

## 1. How to read this plan

- **Phases** follow the specification: 1 Foundation, 2 Core archiving, 3 Crawling and sources, 4 Local search, 5 Combined search, 6 Intelligent storage, 7 Discovery, 8 Knowledge packages, 9 Hardening. All nine are in scope.
- **Task IDs** use a letter per phase to avoid clashing with the priority names P1 to P4: **F** Foundation, **A** Archiving, **C** Crawling and sources, **S** Search (local), **O** Online (combined) search, **T** sTorage, **D** Discovery, **Z** ZIM and Wikipedia, **H** Hardening.
- **Scope column**
  - **MVP**: needed to satisfy an acceptance criterion.
  - **v1**: in the nine phases and planned, but no acceptance criterion depends on it; it may slip within the release without failing acceptance.
  - **Post-v1**: designed for and documented, deliberately not built. The reason is given in [section 12](#12-deferred-and-partly-deferred-requirements).
- **Each task** is small enough for one review, independently testable, and names its tests. "Unit" means Vitest with no I/O, "integration" means Vitest with real SQLite and the local fixture sites, "e2e" means Playwright against the Compose stack. **No test touches the real internet**; fixtures are local sites and fake providers.
- **Definition of done for every task:** typecheck and lint clean, tests listed pass on AMD64 and ARM64 CI, documentation updated if behaviour or configuration changed, no new network access outside the SSRF-guarded fetcher.

### Sequencing at a glance

```
 F (foundation)
  |
  +--> A (core archiving: capture one page, browse it offline, reader)
        |
        +--> C (crawling, sources, downloads, schedules, link states)
        |      |
        |      +--> T (storage: priorities, retention, eviction)  <-- needs sources + volumes
        |      +--> D (discovery)                                  <-- needs T, S, links
        |
        +--> S (local search) --> O (combined search) --> D (search-driven discovery)
        |
        +--> Z (ZIM, Wikipedia)   <-- needs A listener, S/O merge, C crawl engine
 H (hardening) runs from F onward as tests; the dedicated phase closes gaps
```

Phases 3 and 4 can overlap after A-13 (the listener) and A-08 (extracted text) exist. T-01 to T-04 (pure planner) can start as soon as the data model is migrated in F-03, in parallel with C.

**F-03 spike result (2026-11-01).** `drizzle-kit` 0.31.11 with `drizzle-orm` 0.45.4 and `better-sqlite3` 13.0.3: `generate` works against the schema and emits plain `CREATE TABLE` plus partial and `DESC` indexes, and `generate --custom` scaffolds an empty SQL file. It **cannot emit `STRICT` tables**, `COLLATE NOCASE` on a column, or `CHECK`s except ones declared by hand with `check()` (the `enum` option on `text()` is type-only). So the migrations are hand-written SQL (`packages/db/migrations/NNNN_name.sql`, applied by our own runner with checksums and a `VACUUM INTO` backup), and the Drizzle schema in `packages/db/src/schema` exists for query typing only. `packages/db/test/schema-sync.test.ts` compares column names and nullability with the migrated database, so the two cannot drift silently. `drizzle-kit generate` stays available as a diff aid (`pnpm db:generate`, output to an ignored scratch folder) and is never used to produce migrations. Deviations recorded: `download_jobs` and `crawl_jobs` are in migration 0001 (activity_log and volume_reservations point at them) with plain-integer `source_id`, `config_id` and `candidate_id` until those tables exist; the `jobs` claim index drops `run_at` from its middle (see [benchmarks.md](benchmarks.md) and data-model.md section 3.5).

**A-14 spike result, D-5 address-bar sync (2026-11-01).** Real server, real browsers, the fixture article site, `tests/e2e/08-browser-shell.spec.ts`. The shell reads `GET /api/browser/frame-state?frameId=` after every iframe `load` event and keeps up with: an in-frame click on a link to another saved page (the address bar and tab title change to the new page's address, a shell history entry is added, no new frame is made); the browser's own Back and Forward (driven with `history.back()` and `history.forward()`, which move the frame through the joint session history: the shell sees the earlier page through `load` and frame state, and moves its own history index instead of adding an entry); a link to something that is not saved (the listener records the interstitial, so the address bar shows the target address and the tab says "Not saved"); a redirect (a URL that redirected when saved resolves through `page_aliases`, and the address bar shows where the page is). The shell's own Back, Forward and reload re-resolve and re-create the iframe, so they add no joint-history entry. **Chromium and Firefox 157 (the Playwright builds of Playwright 1.64) pass the whole spec.** **WebKit could not be run**: the Playwright WebKit build (v2370) crashes at launch with a segmentation fault on this macOS version, before any page loads. The WebKit run is left to H-11 on a machine where it launches (`E2E_BROWSERS=chromium,webkit,firefox pnpm test:e2e`). The fallback in D-5 (a hash-pinned script with `allow-scripts`) was not needed and is not planned. Two limits seen: the frame-state record is the last document the listener served to the frame, so a very fast second click could be read as one navigation (the sequence number makes the shell apply only newer ones); and the CSP `frame-src` and the token's `frame-ancestors` both name the origin the shell is served from, so opening the app through a second hostname needs `NCB_APP_URL` to match it.

**A-18 spike result, fragment navigation in a sandboxed cross-origin frame (2026-11-01).** The parent calls `iframe.contentWindow.location.replace(url)` on the `sandbox="allow-popups allow-popups-to-escape-sandbox"` frame (cross-origin and an opaque origin, so only `location.replace` and `location.href` are reachable, and that is enough). The first call loads the document with `?hl=<term>` (one request; the listener wraps the matches in `<mark id="ncb-hit-N">`); the next, previous and wrap-around moves change only the fragment (`#ncb-hit-N`), which the browser treats as a same-document scroll: **no document request is made, no `load` event fires, and no joint-history entry is added** (`replace`), asserted in `tests/e2e/11-find.spec.ts`. The current hit is styled with `mark:target` in the injected stylesheet, so no script is needed, and Playwright confirms the target mark is in the viewport after each move. The listener does not record a `?hl=` response as a new document, so the address bar and history do not move. Chromium and Firefox pass; WebKit is as for D-5 above. If a browser cannot drive the frame this way, `pointFrame` falls back to setting `iframe.src` to the same address with `#ncb-hit-N`, which reloads the frame each time but behaves the same otherwise. Native Ctrl+F (Cmd+F) is not intercepted anywhere (asserted for 10 browser-reserved combinations). Find is for the saved page view; in reader view the bar says to use the browser's own find, because `?hl=` is not applied to the reader route yet (deferred).

**C-14 spike result, PDF text extraction (2 November 2026).** Three candidates, run inside a `linux/arm64` `node:24-trixie-slim` container (Node 24.22.2, Docker Desktop VM on an Apple M4 Pro, so timings are optimistic and **not a Pi**): `pdfjs-dist` 6.5.438 (legacy build) in a `worker_thread`, `unpdf` 2.1.0 (a pdf.js build packaged for serverless use), and `pdftotext` from Debian's `poppler-utils` 25.03.0. Three generated PDFs (`scripts/gen-doc-fixtures.mjs`, Chromium `page.pdf()` from the fixture article sentences; CC0, in `tests/fixtures/docs`): 1 page / 42 KB, 24 pages / 114 KB, 240 pages / 776 KB. Each cell is three runs; memory is the peak resident set of the whole process measured with GNU `time` (an idle `node` is 44 MB, so subtract that for the cost of the extraction); `pdftotext` is a child process and its own peak is shown.

| PDF | pdfjs-dist in a worker | pdfjs-dist, main thread | unpdf | `pdftotext -layout` |
|---|---|---|---|---|
| 1 page | 95 to 98 ms, 104 to 109 MB | 75 to 77 ms, 93 to 96 MB | 50 to 53 ms, 80 to 83 MB | 13 to 15 ms, 18 MB (+ node 44 MB if spawned) |
| 24 pages | 137 to 143 ms, 118 to 124 MB | 119 ms, 112 to 113 MB | 83 to 86 ms, 91 to 94 MB | 26 to 27 ms, 18 MB |
| 240 pages | 390 to 422 ms, 144 to 146 MB | 386 to 399 ms, 130 to 133 MB | 326 to 338 ms, 145 to 150 MB | 129 to 130 ms, 19 MB |
| Text characters (1 / 24 / 240 pages) | 3,148 / 74,855 / 749,187 | same | 3,146 / 74,830 / 748,946 | 3,152 / 74,951 / 750,147 |

Findings. (1) **Quality is the same for the engines that matter:** all three extract the same text (character counts within 0.1 %), and `pdfjs-dist` and `unpdf` are the same engine. (2) **A worker thread's heap limit does not bound pdf.js memory**: the 240-page file still finished with `maxOldGenerationSizeMb: 32`, because pdf.js keeps its data in `ArrayBuffer`s outside the JavaScript heap. The memory guard for pdf.js is therefore the upload size cap (50 MB), a page cap (3,000), a text cap (8 million characters), a 60 s timeout and the worker being a separate thread that the pool replaces if it stops answering. (3) `pdftotext` is 3 to 5 times faster and uses a fifth of the memory, and a child process can be killed and capped by the kernel (`ulimit`, cgroups), which is the better isolation; but `apt-get install poppler-utils` adds **73 packages and 72 MB** (cairo, X libraries, gnupg) to the server image, it must be installed on every developer's machine for the tests to pass, and it is a GPL-2.0-or-later program (fine with AGPL when run as a separate executable, but one more thing to ship and audit). (4) `unpdf` adds a dependency for no gain: it bundles its own copy of pdf.js and is faster only on tiny files because it starts less machinery.

**Choice: `pdfjs-dist` (Apache-2.0) in the existing `extract` worker pool.** It needs no system package, runs the same in tests and production, gives page count and metadata (title, author, dates) directly, and fits the memory limits above for the sizes this app accepts (about 145 MB peak for a 240-page, 776 KB file on top of the server). If a real Pi shows the memory is too much, the swap to `pdftotext` is contained in `apps/server/src/imports/pdf.ts` and the Dockerfile. Licence: pdfjs-dist is Apache-2.0 (checked by `pnpm licence-audit`, which passes). Known gaps (no OCR for scanned PDFs, no CMap data for some CJK PDFs, content-stream reading order) are listed in `apps/server/src/imports/README.md`.

**C-14 as built.** `POST /api/archive/import` (multipart, `NCB_IMPORT_MAX_MB`, default 50) stores HTML, PDF, Markdown and text as captures under the Imports system source or a user-made `imported_documents` source (type now enabled), with the checks, conversions and error kinds in `apps/server/src/imports/README.md` and `docs/api.md`. Migration 0008 adds `import_documents`. Imported pages have the synthetic address `https://imports.noconbrain.invalid/<sha256 prefix>/<name>` (never fetched). A PDF is a download of the original plus reader text; the "original" view of an import is the derived text document. Indexing arrives with S-02: the text and reader blobs already exist and `pages.content_type` is `html`, `pdf` or `text` for the Documents category (S-14).

**C-16 as built.** The renderer is its own image (`docker/renderer/Dockerfile`, `apps/renderer`: Playwright 1.64.1 with `chromium_headless_shell` on `node:24-trixie-slim`, one page at a time, a fresh context per page, a browser restart every 50 pages, images, media and fonts not loaded) in the `renderer` compose profile, on the internal-only `render` network, with `mem_limit` 1 GB, `pids_limit` 256, read-only root, tmpfs `/tmp`, `init`, Playwright's seccomp profile and `CAP_SYS_CHROOT` (Chromium's sandbox stays on). `server` runs the guarded forward proxy on that network (`apps/server/src/renderer/proxy.ts`, HTTP and CONNECT, the `@ncb/fetch` SSRF guard on every request, shared-secret authentication, 6 connections per host with 50 ms between new ones, offline refusal, byte caps). After a capture finishes, `triggers.ts` applies the deterministic rules (little text with scripts, empty mount node or `<noscript>` note, Readability and defuddle both failed, or the source's `renderMode: "always"`; never for `renderMode: "never"`, non-HTML, error statuses, never-hosts or an already rendered version) and queues a `render` job (queue `crawl`, pseudo-host `renderer.internal`, so concurrency is `host_state.max_concurrent`). The rendered DOM becomes a second version of the page, `render_mode = 'browser'`, through the normal pipeline, sanitised at serve time. Concurrency: `resources.renderConcurrency` (live; `NCB_RENDER_CONCURRENCY` is only its default, 1). Measured image size and memory per page: [benchmarks.md](benchmarks.md). Details: `apps/server/src/renderer/README.md`.

C-16 deviations and limits. (1) The rendered copy is a second version, not a replacement: under `on_change` versioning the plain shell stays as the older version (under `latest_only` it is superseded). A later refresh of a rendered page fetches the plain shell first, which differs from the latest (rendered) version's bytes, so it makes another plain version before the render makes the next rendered one; the extractor's text-hash check discards a rendered version that is identical to the latest. (2) "DOM and resource capture": the renderer returns only the DOM; the server then fetches the page's assets itself through its own guarded fetcher (stage 3), which keeps every byte of archived content under the same size caps and robots rules, and means the browser does not load images, media or fonts. (3) The proxy cannot see inside HTTPS tunnels, so byte caps on those are per tunnel (100 MiB) plus the renderer's own page budget. (4) The proxy listens on all interfaces inside `server`, so containers on `backend` and `egress` can reach it; it refuses every request without the renderer secret. (5) `docker compose` cannot set `NCB_RENDERER_URL` on `server` only when the profile is on, so turning the renderer on takes two `.env` lines. (6) Rendering needs unprivileged user namespaces on the host. (7) Robots: the render job checks robots.txt for the page itself (a user-initiated save may override it, as for the plain fetch); the browser's sub-requests are not checked against robots.txt. (8) The renderer is checked by a Docker test that needs Docker and builds the arm64 image (`NCB_DOCKER_TESTS=1`); the default `pnpm test:integration` runs the same flow against a stand-in renderer with no browser.
